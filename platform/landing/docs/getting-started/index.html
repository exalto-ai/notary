DEVELOPERS AND OPERATORS

CLI + local service

Two command-line programs for SDK routing, coding-agent configuration, scripting, automation, and explicit service supervision.

Install the macOS app

Choose Download for macOS on the product site. Open the downloaded DMG, move the app to Applications, then launch it. The app guides first-time setup and supervises its bundled local service.

System requirements

  • A Mac with Apple silicon (M1 or newer).
  • macOS 12 Monterey or later.
  • A supported model provider account when you are ready to capture a real interaction.

What the app manages

The app configures capture protection, helps connect a provider or coding tool, starts and stops its bundled notaryd, and embeds the local capture workspace. Provider credentials stay in the tool that sends the model request; the app does not ask for or store them.

Install the CLI and local service

The shell installer supports Apple silicon Macs and x86-64 or ARM64 Linux systems. It selects the complete latest stable release and checks the archive against its published SHA-256 value. The checksum detects corruption but is not an independent signature because it shares the archive publisher.

curl -fsSL %PRODUCT_ORIGIN%/install.sh | sh

Build from source

To build the same two local programs yourself, use Rust 1.95.0 and the public runtime repository toolchain file. That repository contains the complete protocol, daemon, CLI, generic notary, dashboard, updater, and verification implementation. Hosted accounts, billing, admission policy, and the websites are operated separately and are not part of the runtime source tree.

git clone https://github.com/exalto-ai/notary-runtime.git
cd notary-runtime
cargo install --locked --path crates/notaryd --bin notaryd
cargo install --locked --path crates/notaryctl --bin notaryctl

Programs

notaryd is the long-running local service. notaryctl is its short-lived REST client. The command-line archive installs both together.

Install the agent skill

The CLI bundles portable instructions for finding traces, sealing with approval, verifying packages, diagnosing operations, and protecting private evidence. Install them for Codex, Claude Code, or both. The command does not contact or start the daemon. Use --skills-dir /path/to/agent/skills for another Agent Skills compatible client; re-run with --force only after inspecting a different existing skill. Claude Code uses $CLAUDE_CONFIG_DIR/skills when that environment variable is nonempty and ~/.claude/skills otherwise. It detects changes inside an existing personal skills directory; restart it if that directory did not exist when the current session started.

notaryctl skill install --target codex
notaryctl skill install --target claude
notaryctl skill install --target all

Run and configure

Start the service

notaryd

Open the local dashboard

Visit http://127.0.0.1:8788 and use Overview, Traces, Activity, Providers, and Settings. The default loopback configuration opens directly. If admin.auth is enabled, sign in with its configured username and password; the dashboard exchanges them for an HttpOnly session and does not store the password.

Configuration file

The first service start creates an editable config.toml at the standard user location: ~/.config/notary/config.toml on Linux, %APPDATA%\notary\config.toml on Windows, and ~/Library/Application Support/notary/config.toml on macOS. It is written once and never replaced. Start with an explicit file when needed:

notaryd --config /path/to/config.toml

Use the command client

notaryctl is a short-lived client for the daemon's versioned loopback API. It checks daemon health and never opens the metadata store or vault directly. Add --json for automation. Raw capture-list JSON includes stored prompt and output previews, so add --metadata-only before sending structured capture results to an agent transcript.

notaryctl status
notaryctl traces list --provider openai
notaryctl --json traces list --provider openai --metadata-only
notaryctl traces show trc-example --json
notaryctl open

What it controls

config.toml holds the listener address, optional admin authentication, an optional local or self-hosted notary endpoint, filesystem or private S3-compatible artifact settings, SQLite or PostgreSQL metadata settings and preview limits, and the enabled provider routes. SQLite and filesystem storage remain the defaults. All built-in providers start enabled. The hostname and API behavior of each provider remain fixed; configuration cannot direct the proxy to an arbitrary upstream host.

Pause capture without changing clients

Turn capture off in the local dashboard or macOS app to keep the same fixed provider proxy URLs while bypassing admission, the remote notary, capture storage, and evidence creation for new requests. The daemon opens an ordinary WebPKI-verified HTTPS connection to the provider and streams the request and response directly. In-flight requests keep the mode they started with, and the durable setting survives restarts. Turning capture back on initializes the notary first; if that fails, capture stays off rather than silently falling back.

Optional admin sign-in

The loopback administration API is available to local processes without credentials by default. To require sign-in, configure a username and an Argon2id PHC password hash. Store the hash, including its salt and work parameters, rather than the plaintext password.

[admin.auth]
username = "local-admin"
password_hash = "$argon2id$v=19$m=32768,t=2,p=1$..."

Capture encryption is automatic

On first use, the proxy creates a random capture-encryption key and stores it in Keychain on macOS, Credential Manager on Windows, or the desktop secret service on Linux. The OS may ask you to unlock that credential. You do not need to run a separate initialization command.

Optional passphrase mode

If you prefer a passphrase instead of the operating-system credential service, point NOTARYD_VAULT_PASSPHRASE_FILE at a private UTF-8 file before the first service start. An empty passphrase is accepted for low-friction local testing, but it provides no meaningful protection if someone obtains both your captures and vault configuration.

What happens online

The local proxy handles plaintext while the notary participates in the provider TLS connection without seeing application data. Provider response bytes stream back to your agent as they arrive.

What happens at end-of-stream

The proxy seals encrypted deferred state into one .llmcapture. It does not perform the expensive final proof before returning control to your workflow.

Connect a hosted account when needed

Local capture, sealing, and verification do not require an account. Connect one to use account allowances, share a sealed trace, or manage the same device from hosted Settings. notaryctl account connect opens a browser approval flow and stores the rotating device credential only in the daemon credential vault. account show shows the connected identity, plan, and balances without revealing the credential; account disconnect disconnects that device without deleting local evidence.

notaryctl account connect
notaryctl account show
notaryctl account disconnect

Use an API key for unattended hosts

Create a deployment-specific, least-privilege key in hosted Account settings and inject it as NOTARYD_PLATFORM_API_KEY or through the private NOTARYD_PLATFORM_API_KEY_FILE. The complete key is shown once and never belongs in config.toml, logs, or artifacts. One daemon can use an injected API key or a browser-approved device session, never both; revoke API keys from hosted Settings.

export NOTARYD_PLATFORM_API_KEY_FILE=/run/secrets/notary-platform-api-key
notaryd

Connect an SDK

OpenAI
Set your SDK base URL to http://127.0.0.1:8787/openai/v1 and continue using the Responses API.
Codex with a ChatGPT plan
Live-tested with Codex CLI. Add a custom provider with base URL http://127.0.0.1:8787/codex and requires_openai_auth = true. Codex keeps and attaches its own ChatGPT login.
Anthropic / Claude Code
Live-tested with Claude Code. Set the base URL to http://127.0.0.1:8787/anthropic and continue sending Messages API requests with either its API key or its own saved claude.ai login.
DeepSeek
Set the OpenAI-compatible base URL to http://127.0.0.1:8787/deepseek and continue using /chat/completions.
OpenRouter
Set the OpenAI-compatible base URL to http://127.0.0.1:8787/openrouter/api/v1, retain OPENROUTER_API_KEY, and use /chat/completions. Verified origin is openrouter.ai; a namespaced model slug is metadata, not proof of a direct upstream-vendor connection.

OpenRouter + Chat Completions

The model slug remains trace metadata. The resulting evidence authenticates OpenRouter, not the vendor named in that slug. The Authorization, HTTP-Referer, and X-Title header values are hidden in a sealed package.

curl http://127.0.0.1:8787/openrouter/api/v1/chat/completions \
  -H "Authorization: Bearer $OPENROUTER_API_KEY" \
  -H "Content-Type: application/json" \
  -H "HTTP-Referer: https://example.test" \
  -H "X-Title: Capture example" \
  -d '{"model":"YOUR_MODEL","stream":true,"messages":[{"role":"user","content":"Reply with exactly: sealed"}]}'

Where subscription login works

The supported, live-tested clients are Codex CLI with its saved ChatGPT login and Claude Code with its saved claude.ai login. The macOS app can supervise the local proxy, but it does not configure or sign in to either client. Native Claude Desktop cannot use this route. Codex desktop is not yet end-to-end tested or supported. Browser, Slack, remote, and cloud sessions cannot reach the local proxy.

Where the API key comes from

Keep configuring credentials exactly as your SDK or agent expects, for example OPENAI_API_KEY in your shell or secret manager. Nothing here creates, loads, or requires a .env file. A .env file is only one optional way your own application might populate environment variables.

Provider boundary

The first local path segment selects a fixed adapter: /openai, /codex, /anthropic, /deepseek, or /openrouter. Each adapter fixes the upstream hostname and path to an explicit allowlist. The notary, not a caller-supplied URL, resolves and opens the provider connection.

Coding agents

Codex + OpenAI API key

Replace YOUR_RESPONSES_MODEL with a model available to the OpenAI API key. The explicit no-WebSocket capability keeps Codex on the supported HTTP transport.

# Add this to ~/.codex/config.toml:

model_provider = "capture"
model = "YOUR_RESPONSES_MODEL"

[model_providers.capture]
name = "Exalto Capture local proxy"
base_url = "http://127.0.0.1:8787/openai/v1"
env_key = "OPENAI_API_KEY"
wire_api = "responses"
supports_websockets = false

Codex + ChatGPT plan

This flow is live-tested with Codex CLI. First run codex login status and confirm that Codex says it is logged in using ChatGPT. Do not set env_key in this provider. Codex owns the login and refreshes it; the proxy only forwards the request headers and hides every header value from the sealed package. The proof authenticates chatgpt.com and the disclosed bodies, not the account owner, plan, or billing. Codex desktop is not yet end-to-end tested or supported, and cloud work cannot reach the loopback route.

# Add this to ~/.codex/config.toml:

model_provider = "capture-chatgpt"

[model_providers.capture-chatgpt]
name = "Exalto Capture · ChatGPT plan"
base_url = "http://127.0.0.1:8787/codex"
requires_openai_auth = true
wire_api = "responses"
supports_websockets = false

Run Codex

codex exec --ephemeral --skip-git-repo-check \
  'Reply with exactly: hello'

Claude Code + Anthropic API key

Set Claude Code's Anthropic base URL to the local route, keep the API key in its normal environment, and choose a model available to that account.

ANTHROPIC_BASE_URL=http://127.0.0.1:8787/anthropic \
claude --bare --no-session-persistence \
  -p --model YOUR_MODEL \
  'Reply with exactly: hello'

Claude Code + claude.ai plan

Run claude auth status first; Claude Code itself must report a saved first-party login. A login in the native Claude desktop app is separate. Remove apiKeyHelper and do not set ANTHROPIC_API_KEY or ANTHROPIC_AUTH_TOKEN. Claude Code owns login and refresh; the proxy forwards its authorization and Messages protocol unchanged and hides every header value from the sealed package. The proof authenticates api.anthropic.com and the disclosed bodies, not the account owner, subscription, or billing. Native Claude Desktop, web, Slack, remote, and cloud sessions do not run through this local route.

env -u ANTHROPIC_API_KEY -u ANTHROPIC_AUTH_TOKEN \
  ANTHROPIC_BASE_URL=http://127.0.0.1:8787/anthropic \
  claude -p 'Reply with exactly: sealed'

OpenCode + DeepSeek

Set the provider base URL to http://127.0.0.1:8787/deepseek and retain DEEPSEEK_API_KEY in the OpenCode environment.

Work with local traces

Search local traces

Each completed provider interaction keeps its vault-encrypted capture in the selected private artifact store and gains a row in the selected metadata store. Use the dashboard, or fetch the live OpenAPI document and query the local admin API:

curl "http://127.0.0.1:8788/v1/traces?query=pricing&provider=openai"

Search punctuation safely

Capture search treats punctuation as text boundaries instead of raw full-text-search syntax. Hyphenated terms, emphasis marks, multiple words, and double-quoted phrases return matches or an empty list through the normal JSON response.

Filter traces and activity

The service applies trace status and activity severity and type filters before returning bounded results. Coding agents should discover state, status, provider, event type, severity, and time filters from the live OpenAPI document instead of reimplementing them client-side.

GET /v1/traces?status=notarization_failed&limit=20
GET /v1/activity?severity=error&event_type=notarization_failed&limit=20

What trace metadata records

A trace records its provider, request and response model when available, HTTP status, request and response sizes, duration, state, operational status, and retained artifact facts. By default, it indexes the first 1,000 characters of the request prompt and output as plain local text. It does not store header values, cookies, or credentials. Change the metadata path, disable full-text search, or set either preview limit to 0 in config.toml.

Stopping and retrying

Once the end-of-stream capture is sealed, stopping the proxy does not invalidate it. Sealing into a portable package can happen later. Retry a failed or interrupted attempt through the owning trace; the unchanged capture is retained, although interrupted proof computation starts over.
